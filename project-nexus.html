Nexus — Linux Penetration Test

An independent assessment tracing an attack path from web and virtual-host discovery to credential-based CRM access, an application shell, SSH as a local user, and root through an unsafe scheduled template synchronization workflow.

Assessment summary

I began with port discovery, followed by web and virtual-host enumeration using ffuf/Gobuster. Reviewing the accessible Gitea instance revealed credentials in repository history. Those credentials provided CRM access. I then used Burp Suite to inspect and manipulate an email-related application request and obtained a reverse shell.

From the web shell, I found the application's .env file. Its credentials enabled SSH access as jones, where I continued host enumeration and captured the user flag. For privilege escalation, I inspected systemd timers, found the template synchronization service, and identified unsafe path handling in its custom script. The scheduled service provided a route to a root shell.

Port discovery→Web enumeration→Exposed credentials→CRM shell→SSH as jones→systemd timer→Root

Methodology

1. Port and web discovery

The initial scan identified SSH and HTTP. Web discovery and virtual-host enumeration exposed git.nexus.htb and billing.nexus.htb. The billing host redirected to the Krayin CRM login page.

2. Credential discovery and CRM access

Reviewing Gitea commits revealed database configuration secrets. I tested the recovered credential against the CRM in the authorized lab and gained access. This demonstrated how secrets in source-control history and credential reuse can expose a separate application.

3. Application shell and user flag

I examined the CRM's email functionality with Burp Suite and used a web reverse-shell payload to obtain a www-data shell. Local application configuration exposed credentials that I used to authenticate over SSH as jones. I continued enumeration and retrieved the user flag.

4. Root through the scheduled synchronization service

Systemd timer enumeration revealed a timer that triggers Gitea template synchronization. I reviewed its service configuration and the custom Python script. The script combined a staging directory with repository-controlled paths and wrote files without sufficiently constraining the destination to the staging root. Since the service ran with elevated privileges, this unsafe write behavior enabled escalation to root.

CVE analysis: I researched CVE-2026-25718 during the investigation because it concerns unsafe path handling in Gitea template generation. My notes identify Gitea 1.26.0, while that advisory lists versions before 1.25.5 as affected. The evidence I recorded points to the separate root-run synchronization script as the direct escalation path; it does not establish that the installed Gitea version was affected by that CVE.

Independent solve

I completed this machine without consulting a walkthrough. When I got stuck on the root path, I used one HTB guided-mode prompt asking which systemd timer triggered template synchronization. I then enumerated the timers, inspected the matching service and script, researched the behavior, and worked out the escalation myself.

What I took away

  • Review repository history when looking for leaked or reused credentials.
  • Validate secrets against the intended service and avoid credential reuse across systems.
  • Use request inspection to understand application behavior, then verify the root cause before assigning a vulnerability class.
  • Inspect systemd timers, service definitions, execution users, and custom scripts during Linux privilege-escalation analysis.
  • Constrain filesystem writes to a verified directory and run scheduled jobs with least privilege.

How to read the evidence

  • Discovery creates leads. An open SSH or web port tells an analyst which services to inspect. Virtual-host enumeration then checks whether the same web server presents different applications for different hostnames; finding a login page is a lead, not a vulnerability by itself.
  • A secret in repository history remains exposed. Deleting a secret from the latest file does not remove older commits. Testing the recovered credential against the CRM showed the practical impact of credential reuse within this authorized lab.
  • Keep application access and operating-system access distinct. The CRM shell ran as the web-service account. Credentials in local application configuration then enabled a separate SSH session as jones; that transition is evidence of credential exposure, not proof that the web account already had the user's privileges.
  • Privilege escalation came from the scheduled service's trust boundary. A systemd timer starts a service on a schedule. Reviewing the service identity and its Python script showed that repository-controlled paths influenced writes performed by a privileged service. A privileged process must canonicalize and confine destinations to its intended directory.
