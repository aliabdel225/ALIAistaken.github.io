01 / Case overview

Start with what the file can prove

The investigation began by classifying the sample and recording stable identifiers. Those facts help select the right tools and preserve a reproducible chain back to the analyzed file.

Initial classification

The ELF header identifies a 64-bit little-endian x86-64 position-independent executable. It is dynamically linked and depends on liburing.so.2 and libc.so.6. The visible symbol table is not stripped, which makes named functions useful investigation pivots.

02 / Investigation method

Follow evidence from broad to specific

The workflow moved from file identity to program behavior. Each step was chosen because the previous evidence suggested what to inspect next.

Classify the artifact

Check file type, hash, ELF header, dependencies, and protections. This establishes architecture, runtime requirements, and whether later disassembly should be straightforward.

Use strings as leads

Paths such as /proc/net/tcp, /var/run/utmp, and tracing files expose likely host-survey and defense-interference routines. Treat strings as leads, then confirm cross-references in code.

Map functions to behavior

Named functions including cmd_users, cmd_ps, cmd_privesc, and cmd_killbpf make it possible to trace paths, API arguments, branches, and output.

Trace the network loop

Follow main through socket creation, address setup, connect, receive, and dispatch. This reveals the hard-coded endpoint and the reconnect delay.

Confirm dispatch semantics

Inspect process_cmd and its comparisons to distinguish accepted command forms from invalid input and to connect each command to its handler.

State confidence and limits

Separate directly observed code facts from behavioral inference. Record that dynamic execution did not occur, so no live C2 exchange or host changes were observed.

03 / Behavioral findings

What the agent is built to do

The conclusions below are based on strings, named functions, and the supplied disassembly. “Attempts to” describes code intent; it does not claim successful execution on a host.

F01

Outbound command channel

The program creates an IPv4 TCP socket and connects to hard-coded 192.168.56.1:4445. After a failed connection, the reconnect path sleeps for 120 seconds before trying again.

F02

Asynchronous I/O through io_uring

The agent uses Linux io_uring submission/completion queues for socket operations and many file operations. This can complicate telemetry that focuses narrowly on traditional syscall call paths; it does not make activity inherently invisible to the kernel or every EDR.

F03

Host and session discovery

It reads /var/run/utmp to enumerate logged-in users, reads /proc/net/tcp for TCP socket information, and traverses /proc to collect process names and session details.

F04

Privilege and defense reconnaissance

The privesc routine scans /usr/bin and reports SUID candidates. It is enumeration, not an implemented privilege escalation exploit. The BPF routine searches process maps for anon_inode:bpf-map and attempts to kill matching processes.

F05

Tracing interference and cleanup

The agent attempts to write 0 to /sys/kernel/debug/tracing/tracing_on, then interacts with other tracing controls and removes entries under /sys/fs/bpf. Its self-delete routine resolves /proc/self/exe and attempts to unlink that path.

F06

Remote file operations

get reads a requested local path and sends its contents. recv receives a requested amount of data and writes it to a destination path. The implementation uses fixed-size buffers and should be reviewed for transfer framing, bounds, and partial-transfer handling.

06 / Defensive relevance

Detection and investigation ideas

Translate code behavior into observable events. The strongest detections combine process context, network activity, and unusual access to kernel-facing paths.

Correlate the behavior chain

Look for an unusual process creating outbound connections to 192.168.56.1:4445, then reading utmp, /proc, or /proc/net/tcp, followed by writes to tracing controls or BPF filesystem changes. Alert on the sequence and process ancestry, not a single string.

Cover asynchronous I/O telemetry

Validate that endpoint monitoring captures io_uring submission and completion activity, including operations associated with sockets and files. Compare it with network and filesystem telemetry; do not assume syscall hooks alone provide complete coverage.

Investigate BPF related process termination

Correlate SIGKILL events with reads of /proc/*/maps and searches for BPF map mappings. Review whether a privileged process is disabling tracing or deleting objects under /sys/fs/bpf.

Preserve evidence before cleanup

Collect the executable, hash, process metadata, socket records, relevant audit/EDR events, and filesystem timestamps before remediation. Self-unlinking removes a pathname but does not securely erase already-open file content or other forensic traces.

Analysis limitation: The binary was not executed during this investigation. Launching it stopped before its main routine because the analysis VM lacked liburing.so.2. Therefore the endpoint, commands, and destructive actions described here are code-level findings; no successful C2 connection or host modification was observed.

07 / Scope and confidence

What this case study does and does not establish

Established by static evidence

Hard-coded endpoint values, referenced paths and strings, command dispatch, function call sequences, operation arguments visible in disassembly, and the intended control flow.

Not established without runtime evidence

Whether the server was reachable, whether commands were accepted by a server, whether permissions allowed each operation, whether kernel policy blocked tracing changes, or whether the sample completed any destructive behavior.

How to interpret static-analysis findings

  • Start with identity and requirements. The hash, ELF architecture, dependencies, and symbol information tell you which artifact was examined and which analysis tools are appropriate. They do not establish that the file is malicious on their own.
  • Treat strings as navigation clues. A path or command embedded in a binary suggests a routine to inspect. Cross-references and control flow are what connect that clue to a function and support a behavioral conclusion.
  • Separate code intent from observed execution. Disassembly supports statements such as “the program attempts to connect” or “the handler reads a file.” Because the sample was not executed, this case study does not claim a successful live C2 session, persistence, or changes to a host.
  • State defensive impact precisely. The use of io_uring may complicate monitoring built around a narrow set of traditional syscall paths, but it does not make activity universally invisible. Detection should combine process, network, file, and kernel telemetry.
