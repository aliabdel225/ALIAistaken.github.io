01 / Overview

Executive summary

I assessed a deliberately vulnerable Linux host in a private training environment to understand how service exposure, weak authentication, and excessive permissions could compound into a larger compromise. I began with network reconnaissance, enumerated a WordPress installation, tested credentials in the authorized lab, and investigated application and database artifacts after obtaining SSH access.

The source report describes authenticated access as michael, examination of WordPress configuration and MySQL, password recovery related to steven, and a possible path to root through privileged Python execution. The available record does not include all command output required to independently prove each claimed privilege boundary was crossed.

02 / Engagement design

Scope, tools & methodology

In scope: Target 1, 192.168.1.110, on a private training subnet. Approach: discovery → enumeration → authentication assessment → authenticated investigation → privilege review → remediation. Primary tools: Nmap, WPScan, Gobuster, Hydra, John the Ripper, SSH, Linux shell, and MySQL client.

My first priority was to establish what the host exposed before choosing a testing path. I treated each service as a lead to investigate, not an automatic vulnerability. I then correlated web-enumeration results with authentication and filesystem findings to build an attack narrative.

Service discovery→WordPress enumeration→Credential testing→SSH foothold→Application / DB review→Privilege review

03 / Technical walkthrough

Attack chain, step by step

PHASE 01

Network reconnaissance

I used Nmap to identify reachable services and narrow my investigation. The report records SSH (22), HTTP (80), RPC-related service (111), and NetBIOS/SMB (139/445). This gave me several potential paths, with SSH and the web application becoming the focus of the documented assessment.

nmap -sS -sV -p 22,80,111,139,445 192.168.1.110

Reasoning: Service/version enumeration supports targeted follow-up checks. The ports listed here are from the original report; this illustrative command is not represented as a verbatim captured command line.

PHASE 02

Web application and identity enumeration

I examined the web application and used WPScan to investigate WordPress users. Gobuster supported directory discovery. The goal was to identify authentication surfaces and potentially sensitive paths, then test hypotheses rather than rely on assumptions.

wpscan --url http://192.168.1.110/wordpress --enumerate u
gobuster dir -u http://192.168.1.110 -w /path/to/wordlist.txt

Reasoning: Discoverable usernames can reduce the work needed for password guessing. Enumeration alone does not establish account compromise or a WordPress software vulnerability.

PHASE 03

SSH credential assessment and foothold

The original report describes using Hydra against the michael SSH account and recovering a working password. It then documents an SSH login to Target 1. I used this authenticated foothold to investigate accessible directories and files.

# Authorized lab only; replace placeholders with approved test values
hydra -l michael -P /path/to/approved-wordlist.txt ssh://192.168.1.110
ssh michael@192.168.1.110

Reasoning: The security weakness is an authentication control that permits a guessable password, not merely that port 22 is open. The original report supports the described login but does not supply a complete Hydra session transcript.

PHASE 04

Post-access file investigation

Following the SSH login, I searched the web root and other accessible locations for training challenge artifacts. The original report records a flag in /var/www/html/service.html and another at /var/www/flag2.txt. I omit the flag values because they do not improve a hiring manager's understanding of the security issue.

find /var/www -type f 2>/dev/null
grep -n -i 'flag' /var/www/html/service.html

Reasoning: File discovery helps establish what an authenticated account can read. In a production assessment, I would document actual permissions, ownership and business impact rather than treat the existence of a challenge file as a vulnerability.

PHASE 05

WordPress configuration and MySQL investigation

The report states that I inspected WordPress configuration and identified database connection credentials, then accessed MySQL and queried WordPress posts for lab artifacts. This illustrates the risk of credentials becoming accessible to an account that should not have that level of application access.

# Verify the exact file path in the original lab
ls -l /var/www/html/wordpress/wp-config.php
mysql -u <authorized-db-user> -p
SELECT post_title FROM wp_posts WHERE post_title LIKE 'flag%';

Reasoning: WordPress normally stores database credentials in wp-config.php. That alone is not a misconfiguration; the key questions are who could read the file, whether the account had excessive database privileges, and whether secrets were reused. The original slides use an inconsistent filename spelling, so I have not claimed that the exact file path was verified.

PHASE 06

Offline password recovery and reported privilege escalation

The original report describes recovering a password for steven using John the Ripper and identifies Python execution through sudo as a possible route to root. It also reports a root-level challenge artifact. However, the provided evidence does not show the full sudo -l policy, the exact sudo invocation, or an id result confirming effective UID 0.

# Evidence that would be needed to verify the escalation
sudo -l
id
whoami

Reasoning: A Python shell command alone does not prove root privileges. I therefore classify this phase as reported, not independently verified in the surviving documentation.

06 / Quality assurance

Verification, limitations & next steps

What I can substantiate

The surviving source material documents the lab target, tool selection, service exposure, described SSH access, application/database investigation and reported escalation path.

What I would capture in a repeat engagement

  • Timestamped Nmap output and an annotated network diagram.
  • WPScan/Gobuster output with sensitive paths and identities appropriately redacted.
  • SSH login confirmation, account identity and relevant filesystem permissions.
  • Sanitized database access evidence, with passwords and hashes removed.
  • sudo -l, the exact privilege-escalation step and id output if root access is claimed.
  • Retest results showing remediation effectiveness.

This assessment overlaps with my larger full-scope capstone on the same vulnerable network. I treat it as a focused technical case study, not a separate production engagement.

07 / Professional reflection

What this project taught me

The key lesson was how seemingly separate weaknesses can form an attack chain: discoverable services and identities, weak authentication, application access, and potentially excessive privileges. Just as important, I learned that a strong security report must distinguish observation from inference. A hiring manager should be able to follow my reasoning, understand the control failure, and see exactly what evidence would be required to reproduce or validate the outcome.
