Project story

From basic domain administration to tested security controls

The goal was not just to make a domain work. I wanted a repeatable environment that joins core IT support tasks—account provisioning, workstation enrollment, policy delivery, access troubleshooting—with the audit evidence a security analyst would need.

I started with DNS and domain services, created a departmental OU structure, joined a Windows 11 client, and verified domain authentication. I then built a workstation security baseline, hardened password and lockout policy, enabled useful Windows audit sources, and deployed host-firewall settings through a dedicated endpoint-protection GPO.

Technical walkthrough

How I built, secured, and validated the environment

This project follows an administrator-to-analyst workflow: first establish a functioning Windows domain, then apply security controls, deliberately test them, and examine the resulting evidence. The existing screenshots below document the implementation and validation.

1. Build an isolated enterprise network

I used Oracle VirtualBox and the HOME-WORLD-NET NAT network (10.10.10.0/24) to connect the Windows Server 2025 domain controller, Windows 11 client, and a Kali Linux testing machine. Isolation made it possible to test security controls without targeting production systems.

HW-DC01: 10.10.10.10 | HW-CLIENT01: 10.10.10.20 | Kali: 10.10.10.5
2. Configure Active Directory and DNS

I configured Active Directory Domain Services and DNS on HW-DC01 for HOMEWORLD.LOCAL. Centralized domain services allow administrators to manage identities and computers from one place rather than maintaining unrelated local accounts on each workstation.

3. Join the workstation and verify Group Policy

I joined HW-CLIENT01 to the domain, organized identities using departmental Organizational Units and groups, and checked policy delivery with gpresult. This demonstrated domain enrollment, central configuration, and practical troubleshooting of applied policies.

gpresult /r
4. Enforce password and account lockout controls

I configured a 15-character minimum password length, password history of 24, complexity requirements, and account lockout after 10 failed attempts. I tested the threshold with a lab account, verified the lockout state and Event ID 4740, then unlocked the account and checked that the counters reset. This connected policy configuration to observable security behavior.

5. Enable and investigate Windows auditing

I examined authentication and security records in Windows Event Viewer, including successful logons (4624), failed logons (4625), account lockouts (4740), and process creation auditing (4688). I also worked with PowerShell script block logging (4104). These records provide the evidence needed to investigate account misuse and suspicious execution.

6. Test network exposure and access controls

From the authorized Kali machine, I used network reconnaissance to inspect services in the isolated subnet. I also tested SMB shares, access restrictions, SMB hardening, and Windows Defender Firewall controls. The objective was to verify that permitted access worked and unauthorized access was restricted.

Project outcome: A working Windows domain with tested identity, workstation, authentication, auditing, and network-access controls. The value of the project is the repeatable sequence of configuration, controlled testing, and documented verification—not merely the installation of Active Directory.

How to read the evidence below

For each evidence item, look for four things: the configuration or command, the security or business reason for it, the test performed, and the observed result. The original screenshots remain available at full resolution and should be treated as the primary proof of implementation.

I configured a 10-attempt threshold with a 15-minute duration and reset window, enabled Administrator lockout, then tested a lab user through the full detection and recovery path.

Important distinction: Windows displayed an “invalid credentials, delaying next attempt” backoff earlier in the test, but Active Directory did not mark the account locked until the configured threshold of 10. Client-side delay and domain account lockout are related protections, not the same state.

Analyst notes

Troubleshooting lessons and evidence limits

  • DNS comes first in Active Directory troubleshooting. The workstation points to HW-DC01 for domain DNS so it can locate domain services; public DNS alone would not provide AD service discovery.
  • Configuration and enforcement are different claims. I paired GPO editor screenshots with client-side gpresult, Active Directory queries, event records, or the firewall ActiveStore.
  • Backoff is not lockout. The client delayed attempts before the directory’s 10-failure threshold; I used Get-ADUser and Event 4740 to determine the actual domain state.
  • Scope matters. Workstation security and firewall GPOs are linked to the Workstations OU to avoid unintentionally applying endpoint controls to the domain controller.
  • Lab boundary: this case study proves configuration and local validation in an isolated environment. It does not claim production scale, compliance certification, or complete SIEM coverage of every host and event source.
