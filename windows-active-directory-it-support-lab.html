Windows Active Directory & IT Support Lab

A virtualized Windows domain environment built to practice centralized identity administration, workstation management, support workflows, and foundational security monitoring.

Environment: VirtualBox · Windows Server domain controller (DC01) · Windows client (Client01) · Kali Linux
Focus: Active Directory · DNS/domain connectivity · Users and groups · Group Policy · File shares · Remote access · Windows event logging

Project overview

I built a small, isolated Windows enterprise-style environment to connect everyday IT support responsibilities with the identity, access, and security controls that underpin a managed Windows network. The lab provided a place to work with domain administration, endpoint configuration, troubleshooting, and security telemetry without touching production systems.

Workstreams and technical reasoning

1. Domain services and workstation enrollment

Set up a Windows domain with a domain controller and Windows client. Practiced domain membership and the dependencies between client DNS configuration, domain discovery, and authentication. A client that cannot locate the domain controller may appear to have an account problem even when the underlying issue is networking or name resolution.

2. Identity and access administration

Worked with Active Directory user and group organization, including organizational units and group-based management. This models common help desk requests such as account provisioning, access changes, and investigating sign-in failures. Group-based access helps reduce the risk of inconsistent individual permissions.

3. Group Policy and endpoint management

Explored organizational units and Group Policy to understand how workstation settings can be managed centrally. In a larger organization, consistent policies reduce configuration drift and make support and security baselines easier to maintain.

4. File sharing and remote connectivity

Practiced Windows shares and remote administration concepts including SMB and RDP. These services are useful for support but require attention to permissions, host firewalls, authentication, and network reachability.

5. Event collection and troubleshooting

Configured Windows security telemetry using Sysmon and Winlogbeat and reviewed events in an Elastic/Kibana workflow. Validated Sysmon process-creation telemetry (Event ID 1) to establish that endpoint activity was reaching the monitoring environment. This connects ordinary troubleshooting with security investigation and evidence collection.

Representative validation workflow

ipconfig /all — inspect the client's addressing, DNS servers, and domain-related network settings.

nslookup <domain-name> — verify name resolution before troubleshooting domain sign-in.

whoami /groups — review the signed-in user's group context when diagnosing access.

gpresult /r — identify applied Group Policy and troubleshoot missing settings.

Get-WinEvent -LogName Security -MaxEvents 10 — inspect recent security events as an initial log-health check.

These are representative troubleshooting commands, not a claim that every command output was preserved as project evidence.

Evidence and validation

This section separates confirmed lab observations from screenshots and artifacts that have not yet been supplied. It does not use fabricated console output or stock screenshots as proof.

EV-01 · Sysmon process creation Validated

Observed result: Sysmon Event ID 1 (Process Create) was successfully generated and observed during Windows endpoint logging tests. This establishes a concrete endpoint-telemetry validation point; it does not, by itself, prove full end-to-end coverage of every event source.

Evidence to attach: a screenshot of the Sysmon Operational log showing Event ID 1, plus the corresponding Kibana document if available. Preserve timestamp, host name, event ID, and process fields; redact personal paths or sensitive values.

EV-02 · Domain controller and joined client Screenshot needed

Evidence to attach: Active Directory Users and Computers on DC01, and Client01's domain membership or whoami /fqdn output. These demonstrate the identity environment and client enrollment independently of the architecture diagram.

EV-03 · Users, groups and OUs Screenshot needed

Evidence to attach: an ADUC view of lab OUs and test accounts, alongside a group membership or permissions view. Use fictional lab accounts and obscure any secrets.

EV-04 · Group Policy Output needed

Evidence to attach: a GPO configuration screenshot and a client-side gpresult /r or gpresult /h report proving policy application. A configured GPO alone does not prove it applied.

EV-05 · DNS, SMB and remote access Output needed

Evidence to attach: sanitized DNS resolution, a test share with effective permissions, and any successful RDP/SMB connection tests. Record both the test and result; do not treat a service being enabled as proof of access.

Validation playbook

Run these checks inside your own isolated lab to capture reproducible evidence. They are instructions for future verification, not transcripts of commands already executed.

Domain and DNS checks — Client01

ipconfig /all
nslookup <your-lab-domain>
whoami /fqdn
whoami /groups

Why: confirms client addressing, domain DNS lookup, authenticated domain identity, and effective group membership. Capture the command and the relevant result in one screenshot.

Group Policy validation — Client01

gpupdate /force
gpresult /r
gpresult /h C:\Windows\Temp\gpo-report.html

Why: checks whether the intended computer/user policies are applied, not merely created on DC01. Save the HTML report after reviewing it for sensitive information.

Windows security and Sysmon telemetry

Get-WinEvent -LogName 'Microsoft-Windows-Sysmon/Operational' -MaxEvents 15 | Select-Object TimeCreated,Id,ProviderName
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational';Id=1} -MaxEvents 5 | Format-List TimeCreated,Id,Message

Why: shows Sysmon log availability and process-creation events. For SIEM correlation, search Kibana for event.code: "1" and filter to the lab endpoint; verify field mappings before assuming the query matches your index.

SMB connectivity check — Client01

Test-NetConnection <server-hostname> -Port 445
Get-SmbConnection

Why: distinguishes port reachability from an established SMB connection. Follow up with a permitted test-share access and a permissions screenshot.
