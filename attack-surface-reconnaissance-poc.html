Attack Surface Reconnaissance & Vulnerability Assessment

How I used OSINT, DNS intelligence, internet-exposure research, web-vulnerability reconnaissance, and Nmap service enumeration to examine the attack surface of intentionally vulnerable training systems.

01 / Executive summary

I performed a multi-stage reconnaissance exercise using the Altoro Mutual demonstration application (demo.testfire.net) and a Metasploitable lab host. I began with public information gathering, moved into DNS and service exposure research, reviewed a potential web application vulnerability, and documented network scanning commands for a deliberately vulnerable server.

02 / Objective, scope and approach

Objective: identify publicly discoverable organizational information, infrastructure metadata, visible network services, potential application weaknesses, and service exposure on a lab server. The emphasis was understanding how reconnaissance informs risk prioritization—not claiming an end-to-end compromise.

Targets: Altoro Mutual's public demonstration application for the OSINT, DNS, Shodan and Recon-ng tasks; a local Metasploitable host at 192.168.0.10 for Nmap/Zenmap. I treated these as distinct environments, not a single attack chain.

Proof-of-concept boundary: the original assignment records answers and commands but does not contain raw DNS responses, Shodan screenshots, full Nmap output, or an XSS request/response pair. Accordingly, a reported XSS possibility is not presented as independently validated exploitation.

03 / Technical methodology and evidence

Phase 1 — Public-information reconnaissance

Google Dorking / OSINT

I used search-engine research to identify a person named as Altoro Mutual's CEO in the training scenario. The worksheet records the name Karl Fitzgerald. This illustrates how public organizational details can be gathered without interacting with internal systems.

Why it matters: exposed organizational names and roles may help an adversary craft targeted impersonation or social-engineering pretexts. The recorded name is an exercise answer, not a verified current corporate appointment.

Phase 3 — Internet-facing service research

Shodan

I reviewed Shodan results for the demonstration target. My notes record ports 80, 443 and 8080 and a server banner of Apache-Coyote/1.1. These findings identify potential web-facing services worth validating.

Why it matters: alternate HTTP ports and server banners may expose additional applications or administrative interfaces. A port being open does not prove that the service is vulnerable; configuration, version, authentication, and access controls require separate validation.

Phase 4 — Web vulnerability reconnaissance

Recon-ng / xssed

I documented installing the xssed module in Recon-ng, setting the source to demo.testfire.net, and running the module. The worksheet records an affirmative answer to whether the application was vulnerable to cross-site scripting.

Validation status: possible XSS finding reported in the original exercise, but no payload, affected parameter, browser execution evidence, or request/response transcript was preserved. A modern repeat test would need those artifacts before a confirmed finding or severity could be assigned.

Phase 5 — Local network service enumeration

Zenmap / Nmap / Metasploitable

I documented a service-version scan against the local lab machine and a command to save the results to a file:

nmap -sV 192.168.0.10
nmap -oN /root/zenmapscan.txt 192.168.0.10

The worksheet also records an NSE script invocation:

nmap -sV --script=/root/Downloads/sci 192.168.0.10

The path /root/Downloads/sci is reproduced from the original notes. The actual script contents and output were not retained, so I cannot identify the vulnerability that script would test.

My original answer described the server as having “all ports open.” Without scan output, that statement is not verifiable and should not be read literally. The defensible conclusion is that I was investigating potentially unnecessary exposed services on a deliberately vulnerable lab system.

05 / Security impact and remediation

Reduce attack surface

Inventory listening services, remove unnecessary software, restrict administrative interfaces, and use host/network firewalls to permit only business-required ports.

Secure web applications

Apply context-aware output encoding, validate input appropriately, maintain frameworks, and test suspected XSS with a documented harmless proof of execution.

Maintain asset visibility

Monitor DNS records, external IP ranges, hosting changes, and exposed services. Reconcile third-party search results with authorized scans.

Verify fixes

Repeat Nmap service enumeration after remediation, review firewall rules, and document before/after results. Confirm web issues with reproducible request and response evidence.

06 / What I learned

This lab taught me to approach reconnaissance as a sequence: first understand what an organization reveals publicly, then identify infrastructure and exposed services, then prioritize potential vulnerabilities for validation. It also reinforced an important reporting discipline: a search-engine result, open port, or vulnerability-tool indication is an investigation lead—not proof of compromise.

If I repeat this assessment, I will capture timestamps, sanitized screenshots, exact command output, the NSE script name and findings, and an explicit evidence trail for any web application vulnerability.
