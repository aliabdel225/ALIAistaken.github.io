Executive summary

In this authorized Hack The Box lab, I followed a compromise chain from service discovery to a publicly accessible packet-capture download, unencrypted FTP authentication, reused credentials and reported Linux privilege escalation. The central lesson is that exposing diagnostic network data can undermine otherwise password-protected services.

Evidence integrity: Nmap enumeration, dashboard details and FTP packet traces were supplied as screenshots. The authenticated access, flags and privilege escalation are documented in my investigation notes but lack corresponding terminal screenshots. Credentials, flags and exploit payloads are excluded from this public report.

Investigation and reasoning

01 — Service discovery

I ran nmap -sV -sC 10.129.145.155 to identify reachable services and obtain version and script results. Nmap reported three open TCP ports: FTP on 21, SSH on 22, and HTTP on 80; 997 other scanned TCP ports were closed. FTP and SSH prompted for credentials, so I prioritized the unauthenticated HTTP interface. This was a deliberate decision to investigate the least-restricted entry point rather than guessing passwords.

02 — Dashboard inspection

The HTTP service presented a Security Dashboard showing a Nathan user context, security-event charts and network-capture statistics. One page listed 72 packets, 69 IP packets, 69 TCP packets and zero UDP packets. The page also offered a PCAP download. Captures are sensitive because they can contain application requests, authentication exchanges and internal addressing.

03 — Predictable download identifier

The first downloaded capture did not reveal a useful lead. I noticed a numbered URL, /data/2, and tried /data/0, which returned a different capture. The key reasoning was that a numeric URL segment might identify stored capture records. This demonstrates exposure through a predictable resource path; a formal IDOR finding would additionally require verifying authorization boundaries across distinct users.

04 — Wireshark packet analysis

I inspected the new PCAP in Wireshark, examining traffic between 192.168.196.1 and 192.168.196.16. The capture showed HTTP requests, TCP session setup, and an FTP control-channel login with USER and PASS commands followed by a successful authentication response. Unlike SFTP, ordinary FTP does not encrypt its authentication commands. The cleartext password was redacted from this public report.

Reasoning: I followed protocol exchanges instead of scanning isolated packet rows. Correlating the FTP request and server response established that the exposed credentials were used successfully in the captured session.

05 — Validating credentials and foothold

According to my notes, the recovered credentials authenticated to FTP and SSH. FTP exposed user.txt, and SSH provided an interactive shell. The cross-service success illustrated credential reuse: one secret disclosure compromised multiple authentication surfaces.

06 — Local enumeration and privilege escalation

With shell access, I performed local enumeration and transferred LinPEAS using SCP. My notes report a privilege-escalation path attributed to CVE-2026-53264, followed by root access and discovery of root.txt. Because the supplied material does not include exploit output, package/kernel verification or an independently verified advisory, the CVE attribution and technical exploit mechanism remain unconfirmed. The reported root outcome is documented as an investigator observation, not independently demonstrated evidence.

Key lessons

This exercise reinforced disciplined enumeration, attention to small URL patterns, protocol-level packet analysis, and understanding how individual weaknesses combine into an attack chain. The strongest confirmed evidence is the transition from accessible network captures to plaintext FTP authentication; the root-stage mechanism requires additional documentation.
