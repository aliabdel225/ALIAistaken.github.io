Phantom: Linux Rootkit Investigation

A Volatility 3 case study investigating a concealed unsigned kernel module, mapping its kernel hooks, and correlating suspicious shells with outbound connections.

Read the Markdown report ↗

Volatility 3 · 2.28.2Ubuntu Linux 6.8.0-87-genericIncident Response

Executive summary

The analysis identified an unsigned out-of-tree module named singularity. It was present in a memory scan but absent from procfs and sysfs module views. Kernel logs recorded its load at 2,490.473832 seconds after boot under PID 2669.

Tracing output associated the module with the sched_process_fork tracepoint and 82 ftrace hook entries sharing callback 0xffffc0b3aac0. Three bash processes had file descriptors 0, 1, and 2 attached to separate established TCP connections to 192.168.200.164:8081.

Privilege-escalation clue

Bash history recorded OPERATOR=access bash. The suspicious variable is OPERATOR, with value access. The history establishes the command and value, but not the module's exact implementation mechanism.

Analyst assessment

The combined evidence supports a rootkit incident: a concealed unsigned module, a process-creation tracepoint hook, 82 ftrace hooks, and three bash processes with remote TCP sessions. The TCP listing hooks are consistent with reducing visibility into network connections. The endpoint 192.168.200.164:8081 is the primary network indicator for follow-up.

How to interpret the memory artifacts

  • Cross-view analysis compares independent representations. A module listed by a memory scan but absent from the normal procfs and sysfs views is consistent with hiding or unlinking. That discrepancy is suspicious, but it becomes stronger when independent kernel-log and tracing artifacts support it.
  • Hooks describe capability, not complete behavior. The tracepoint and ftrace records show kernel locations associated with the module. Because module extraction failed, the report does not claim to have verified the exact conditions or code executed by every hook.
  • Socket descriptors provide session context. Each bash process had standard input, output, and error attached to the same established TCP socket. That pattern is consistent with an interactive remote shell; it does not alone establish who controlled the peer or what commands were run.
  • Build the conclusion from independent evidence. The concealed-module discrepancy, kernel load record, tracing hooks, and shell-associated network sessions reinforce one another. The environment-variable clue is recorded separately because shell history does not prove the module's implementation mechanism.
