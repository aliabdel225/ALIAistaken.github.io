01 / Executive summary

Objective and outcome

In this controlled Cisco Packet Tracer lab, I configured an enterprise-style multilayer switch to distinguish an authorized DHCP server from a rogue server operating in the same VLAN. The objective was to preserve legitimate IP address assignment while preventing an unauthorized DHCP server from supplying client network settings.

The simulation showed the switch dropping a DHCP OFFER received on an untrusted port. The test client also obtained an address and gateway from the authorized service, and connectivity checks to the gateway and authorized server succeeded. The DHCP snooping binding table recorded a client MAC-to-IP-to-port association.

Evidence-based conclusion:

The core rogue-DHCP mitigation scenario passed. One unresolved reporting inconsistency remains: the switch CLI lists DHCP snooping as configured for VLAN 50 but reports no operational VLANs. The report treats that as a follow-up item rather than claiming full production-readiness.

02 / Environment and architecture

A segmented switch with competing DHCP sources

The lab uses a Cisco 3560 multilayer switch, several departmental VLANs, a legitimate DHCP server, a test workstation, and a rogue DHCP server. VLAN 50 isolates the DHCP security experiment from other departmental devices.

Trust boundary

Only the interface facing the authorized DHCP server, Fa0/6, is trusted to deliver server-side DHCP messages.

Attack surface

Fa0/8 connects to the rogue DHCP server. DHCP snooping should discard server-side DHCP responses received on that untrusted interface.

03 / Implementation

Configuration and test method

I enabled DHCP snooping globally, scoped it to VLAN 50, trusted the authorized server-facing port, and kept the client and rogue-server ports untrusted. I then renewed the test workstation's DHCP lease and inspected the resulting switch binding table and packet flow.

04 / Evidence

Observed security behavior

Finding A — Rogue DHCP OFFER was dropped

The PDU inspection identifies the source as ROUGE_SERVER and the ingress interface as FastEthernet0/8. Packet Tracer explicitly states that the switch received a DHCP OFFER on an untrusted port and dropped the packet. This is the clearest evidence of enforcement in the lab.

Finding B — Switch learned a legitimate client binding

The DHCP snooping binding table associates the test client MAC 00:D0:97:0E:00:A0 with 192.168.50.150, VLAN 50, and interface FastEthernet0/7. The displayed lease duration was 86,400 seconds.

Finding C — Trust policy matched the intended design

The switch reports Fa0/6 as trusted and Fa0/7 and Fa0/8 as untrusted. The same output confirms that DHCP snooping is globally enabled and configured for VLAN 50.

Finding D — Authorized network connectivity remained available

The test PC received 192.168.50.150/24, gateway 192.168.50.1, and DNS 8.8.8.8. Pings to the gateway and authorized DHCP server each returned four replies with zero packet loss.

Important limitation — CLI status mismatch

show ip dhcp snooping reports DHCP snooping configured on VLAN 50 but operational on no VLANs. This conflicts with the simulation's observed drop behavior and the presence of a binding. The lab evidence supports the specific simulated mitigation test, but the discrepancy must be investigated before extrapolating to production equipment. Packet Tracer is a simulator and may not replicate every platform behavior.

Recommended follow-up checks

  1. Review the VLAN 50 configuration, interface status, and platform-specific DHCP snooping requirements.
  2. Repeat DHCP DISCOVER/OFFER exchanges while monitoring the switch's operational-status output.
  3. Confirm that authorized and unauthorized DHCP server behavior remains consistent across repeated client renewals.
  4. For a real deployment, add DHCP rate limits on untrusted access ports, test logging and alerting, and verify switch software support.
06 / Security analysis and reflection

What this lab demonstrated

A rogue DHCP server does not need to compromise a router to disrupt a local network. If it can answer DHCP requests faster than the legitimate service, it may influence client addressing, gateway selection, or DNS configuration. DHCP snooping reduces that risk by treating switch access ports as untrusted unless they are explicitly authorized to carry DHCP server responses.

The most useful part of this exercise was validating the security control at multiple layers: configuration inspection, a learned binding, client-side address assignment, successful reachability, and an explicit packet-drop event. Together, these observations provide stronger evidence than a configuration screenshot alone.

The operational VLAN reporting inconsistency was also an important troubleshooting lesson. A configuration command being present is not equivalent to proving a control is operational. I therefore separated confirmed outcomes from unresolved status reporting rather than presenting the lab as a flawless deployment.

Skills practiced

Layer 2 switch hardening, VLAN segmentation, DHCP DORA analysis, trusted/untrusted port policy, CLI verification, PDU inspection, and network troubleshooting.

Next security control

07 / Conclusion

Outcome

This lab demonstrated that an appropriately defined switch trust boundary can reject a rogue DHCP OFFER without preventing the test client from receiving a legitimate DHCP lease. The evidence includes the switch's packet-drop decision, DHCP snooping binding state, trust configuration, and successful client connectivity.

Final assessment: Core proof-of-concept successful; one operational-status inconsistency remains open for further verification.
