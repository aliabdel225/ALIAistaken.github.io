I investigated a suspicious scheduled task in the Alliance environment, pivoted from Task Scheduler records to Windows process-creation events, and reconstructed the earliest observed login using a session identifier and RDP registry telemetry.

Investigation summary

The hunt began with a hypothesis that a scheduled task had been disguised as routine administrative activity. I reviewed Task Scheduler Operational events, compared common Windows task names with less frequent entries, and identified the root-level task /SQLConnectvity. Its spelling resembles “SQLConnectivity” but omits an “i,” making it stand out from the expected baseline.

I pivoted to Windows Security process-creation events (Event ID 4688). Two records showed SQLBackup.exe executing from C:\Users\Public\Pictures\ on alliance-central. The filename looks like an ordinary backup utility, while the Public Pictures directory is an unusual location for an executable. This provided a plausible task-to-payload lead despite limited direct Task Scheduler evidence.

Task Scheduler events→Unusual task name→4688 process events→Suspicious executable path→RDP session origin

Scope and telemetry

I worked in the provided Elastic SIEM using the logs-* data view. The initial Task Scheduler search returned 252 records: 10 Event ID 106 records and 242 Event ID 140 records. Most task names were standard Windows maintenance tasks, so I compared the task-name field against that baseline to find the outlier.

Hunt workflow

  1. Reviewed event-code distributions and narrowed the dataset to Task Scheduler Operational events.
  2. Compared frequent built-in task names with less common names in winlog.event_data.TaskName, identifying /SQLConnectvity.
  3. Pivoted to Event ID 4688 on alliance-central and reviewed the two process records for SQLBackup.exe.
  4. Checked the Event ID 4104 script block for the SQL connectivity-check command, without treating it as proof of the payload link.
  5. Because direct logon records were incomplete, correlated process events by logon ID and checked Sysmon registry telemetry for the RDP CLIENTNAME. The originating client was kali.

Example Elastic/KQL pivots used during the investigation:

  • event.code: "140" — review task-update events and task names.
  • event.code: "4688" and host.name: "alliance-central" — review process creation on the SQL host.
  • message: "0x7b9417" — correlate records associated with the session logon ID, then sort by @timestamp ascending.
  • event.code: "13" and host.name: "alliance-ws07" and winlog.event_data.TargetObject: *CLIENTNAME* — inspect the RDP client-name registry event.

Recommended defensive actions

  • Preserve full task XML and audit registration, update, and execution events before logs rotate.
  • Collect the executable for hash, signature, and static analysis; quarantine it if it is not approved.
  • Review the task action, trigger, principal, ACLs, creator, and parent process against an approved baseline.
  • Investigate the account and RDP session associated with the earliest activity; reset credentials and revoke sessions if compromise is confirmed.
  • Improve retention and auditing for Task Scheduler, Security process creation, PowerShell script blocks, and Sysmon registry events.

Analyst takeaway: A common-looking name is not enough to establish legitimacy. Validate the executable path, execution context, parent process, and timeline, then state clearly where missing telemetry limits attribution.

What the event sources contribute

  • Task Scheduler events describe task changes. Event ID 106 records task registration and Event ID 140 records an update. They help locate unusual task names and changes, but the task's action, principal, trigger, and full definition determine what it would run.
  • Process creation records show execution. Security Event ID 4688 supports that a process started, with fields such as executable path, account, and parent process helping explain its context. A suspicious path is a reason to investigate the binary, not proof of its purpose.
  • Script and registry events add separate context. PowerShell Event ID 4104 can record script-block content; Sysmon Event ID 13 can record registry value changes such as an RDP client-name artifact. These sources help reconstruct activity when direct logon auditing is incomplete.
  • Correlation is a reasoning step. Matching host, account, time, and session identifiers can connect records into a timeline. A task event and a process event are still separate observations unless task-action or parent-process evidence links them.
